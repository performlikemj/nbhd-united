# Architecture — system map for agents

Read this before touching tenants, containers, provisioning, messaging flow, or OpenClaw config.

## The three planes

```
Django control plane (nbhd-django-westus2, always-on, 1 vCPU / 2 GiB)
  ├── Subscriber console API (DRF) — serves the Next.js frontend + iOS app
  ├── Channel routers → per-tenant oc-* containers
  │     Telegram poller (apps/router/poller.py) — single-revision, offset in memory
  │     Telegram webhook (apps/router/views.py)
  │     LINE webhook (apps/router/line_webhook.py)
  ├── Billing: Stripe webhooks (dj-stripe) → provisioning
  └── Cron: QStash → apps/cron (bump configs, usage reports, hibernation sweep)

Per-tenant containers (oc-<tenant_prefix>)
  ├── OpenClaw AI assistant runtime (image: nbhd-openclaw:<ocver>-<shortsha>)
  ├── Azure File Share mount ws-<tenant_prefix> (workspace: AGENTS.md, USER.md, memory/)
  └── Managed Identity mi-nbhd-<tenant_prefix> (Key Vault refs use THIS name, not oc-*)

Frontend (nbhd-united-frontend, Azure Static Web App)
  └── Next.js 14 static export (out/) — no SSR
```

DB: PostgreSQL 16 on Supabase **us-west-1**, project `dljqtpunnobyztampxus` (Sydney is deleted; any tool still pointing there is stale — check `max(updated_at) from cron_cronjob` for freshness). Django connects via transaction-mode pooler as role `app_user` (non-BYPASSRLS; RLS backstop is load-bearing).

## Tenant lifecycle

provision → **active** ⇄ **hibernated** (idle ≥2h on `last_message_at`, hourly sweep in `apps/orchestrator/tasks.py`) → **suspended** (billing) → deprovision.

- Hibernation **deactivates revisions**, it does not scale to zero. So `az containerapp list` shows `runningStatus: Running` + `minReplicas: 1` for every tenant — that is a false signal. Trust the **Replicas metric** and per-resource cost queries; `revision list` is also unreliable for "is it running".
- Hibernated tenants **self-heal their image at wake**: `wake_hibernated_tenant` refreshes to `OPENCLAW_IMAGE_TAG` if drifted (single-revision mode auto-activates). Never assume a hibernated tenant is on the fleet image.
- DB-backed features (Fuel/Core/Horizons/settings) are pure Django↔Postgres and work while hibernated; Core and Horizons call OpenRouter directly. The container is only needed for chat. Cold start on first message is expected behavior, not a bug.

## Message flow

Inbound: channel → router (dedup gate `claim_inbound_event`) → PendingMessage queue → drain POSTs to `oc-*` container → OpenClaw runs the turn → response back through the channel sender. iOS chats route **through** the tenant container (iOS is a channel, not a separate brain).

If the container is hibernated, drain triggers wake; wake/hibernate revision ops MUST be idempotent (see invariants.md).

## OpenClaw workspace + config

- Per-tenant config is generated by `apps/orchestrator/config_generator.py` and pushed to the share (`openclaw.json`). Workspace bootstrap files (AGENTS.md persona + gates, USER.md envelope with BEGIN/END sentinels) are also Django-generated and pushed via the sanitize chokepoint.
- Config changes roll out via "bump": pending config marked in DB → `apply_pending_configs` / CI post-deploy step applies them. **Image first, then config** — OpenClaw live-reloads config, so a config that needs a newer image must never land before the image (caused the stream-progress last-good rollback).
- OpenClaw version gates live in `config_generator._parse_version(...)` checks. Fleet default: `OPENCLAW_CURRENT_VERSION` (Tenant field default). Images tagged `<ocver>-<shortsha>`; rollback = bump to a prior tag. `bump_all_tenant_images` is image-only; `bump_openclaw_version --all` does version+config.
- New OpenClaw plugins: smoke-disable first (see `docs/agents/` memory: a bad plugin path wedges boot to last-good config).

## Cost shape (so you don't "optimize" the wrong thing)

~$130/mo for nbhd: Django ~$35 always-on, one active tenant ~$31, hibernated tenants $0. Django **cannot** be right-sized down (Consumption plan fixes 1 vCPU : 2 GiB; live memory working set ~1.07 GiB needs the 2 GiB). Registry churn is handled by the nightly purge task.
